## 2026-06-08 — 自動解改逐步飛入 + 30 秒提示一次只亮一個零件
Type: Implementation
Phase: Phase 4（自動解 / 提示）體驗強化
Feature: 逐步自動解動畫、單零件提示
Commit: (待 commit)
分支: `fix/stepwise-solve-and-single-hint`

### Context
自動解（`F`）原本在單一 frame 內 `board=initialBoard` 後一次迴圈把整份解全部 `board.place()`，視覺上像「直接貼答案」；30 秒閒置提示 `hintCells()` 一次回傳整份解的所有空格，綠色 overlay 一次全亮。使用者要求兩者更像逐步引導：解答一個一個放上去、提示一次只顯示一個零件。配分（自動解 1% / 半透明提示 2.5% / 30 秒延遲 2.5%）已入帳，本次純體驗強化，不改判分邏輯（仍同一份 `Solver::solve` 與 `WinChecker`）。

### AI Contribution
以 Explore 盤點現有架構，找出關鍵槓桿：`animateParts()`（[Renderer.cpp:464](../../src/ui/Renderer.cpp)）的 `1 - exp(-dt*k)` lerp 已會讓「剛轉成 placed 的零件」從 tray 平滑飛向盤面格，因此**不需新寫動畫**——只要把逐一放置分散到多個 frame 即可。提出設計：Game 持有 `solving_/solveStep_/solveTimer_`，新增 `advanceSolve(dt)` 每 frame 推進、`isSolving()` 供 main loop 鎖輸入；`solveAndApply()` 改為只重設乾淨盤面並啟動動畫（不放任何零件，保證零件先在 tray 完成 `visualInitialized`，下一步才有飛入）。`hintCells()` 改成依索引序回傳「第一個仍有 EMPTY 目標格的解答零件」。

### Human Decision / Review
使用者以 AskUserQuestion 拍板兩點：(1) 提示顯示「下一個待放零件」，隨玩家放好自動遞補（非定時輪播）；(2) 解題動畫期間鎖住玩家輸入，按 Backspace / RESTART 可隨時取消並回初始盤面。先計劃後核准（plan mode）再實作。

### Details
- `Game.h`：新增 public `advanceSolve(float)`、`isSolving()`；private `solving_/solveStep_/solveTimer_`。
- `Game.cpp`：
  - `init()` / `resetToInitial()` 加入清除三個解題動畫欄位（換關、重玩、Backspace 都會取消動畫）。
  - `hintCells()` 改為逐零件收集 `pieceCells`，遇第一個非空即 `return`。
  - `solveAndApply()` 改為 `if (solving_) return;`（防重入）→ ensureSolution → 重設乾淨盤面 → 啟動 `solving_=true`、訊息 "Solving..."；**不放零件**。
  - 新增檔案級 `constexpr float kSolveStepInterval = 0.30f`（須 > 0，否則退回瞬間貼上）與 `advanceSolve(dt)`：累加 dt，每滿一個間隔放一個解答零件；放完 `solving_=false`、訊息 "Solved!"、`won = WinChecker::isWon(...)` 觸發勝利音效。
- `main.cpp` in-game 分支：`isSolving()` 時只接受 Reset（Backspace/RESTART）取消，其餘輸入（含 `Input::pollMouse` 直接呼叫 game 的路徑）整段跳過；其後 `game.advanceSolve(GetFrameTime())` 置於讀 `placedCntNow/wonNow` 之前，使每步放置觸發 place 音效並重置 idleTimer（提示維持隱藏），最後一步觸發 win 音效；既有 `setHintsVisible(!wonNow && idleTimer>=30)` 不動。

### Verification / Tests Performed
`cmake --build build-release --target game` 乾淨通過（Game.h 變動連帶重編 main/Game/Input/Renderer，無 warning/error）。GUI 行為（逐一飛入、Solving→Solved 音效、動畫中鎖輸入 + Backspace 取消、閒置 30 秒只亮一個零件並隨放置遞補、雙色 Example5/6）留待使用者實機驗收。

### Result
程式碼完成並通過編譯。自動解與 30 秒提示兩功能改為逐步呈現，邏輯判分不變。

### Risks / Follow-ups
- 飛入動畫成立依賴「先 snap tray 再放置」，間隔須 > 0；目前 0.30f，可依手感微調。
- 放置順序為 parts 索引序（非空間序），視覺上由 tray 上而下飛入，已與使用者確認可接受。
- 待實機 GUI 驗收後再勾穩；Example5/6 雙色需確認顏色/旋轉正確。

### Other Notes
口試可講點：重用既有 lerp 基礎設施、把「跨 frame 狀態機」放在 core（Game）而非 UI、用 `isSolving()` 在 main loop 統一鎖住會繞過 `update()` 的 `pollMouse` 路徑。

## 2026-06-08 — 診斷「varyHard 解不出來」：編輯器匯出無解關 + solver 開場可行性預檢
Type: Debug / Implementation
Phase: Phase 4（自動解）/ Phase 5（編輯器）健壯化
Feature: Solver 開場可行性預檢、編輯器 EXPORT/PLAY 守門
Commit: (待 commit)
分支: `fix/stepwise-solve-and-single-hint`

### Context
使用者回報自動解「太慢」且自製 `varyHard.txt`（從編輯器匯出）「產生不了解答」。需釐清是 solver 太慢/budget 用完，還是關卡本身有問題。

### AI Contribution
寫了兩支 headless 診斷程式（core 不依賴 raylib，可單獨 g++ 編譯）：(1) 計時 + 大 budget 跑 solver；(2) 計算每色「供給=零件格數+固定格」vs「行約束總和 / 列約束總和」的平衡。發現：varyHard 在 2M 與 50M budget 都是**同樣 1.4 秒**回 NO SOLUTION → 搜尋樹完整跑完、非 timeout。平衡檢查揭露 **color 2 供給 16、行/列需求各 12**，差 4 格 → 數學上無解。追到根因在 `Editor::deriveConstraints()`（[Editor.cpp:86](../../src/core/Editor.cpp)）只從**盤面上已放置**的零件推導約束，但 `LevelWriter::write` / `buildPlayableSnapshot` 匯出**全部零件**；匯出時若有零件留在 tray，約束就少算該色 → 匯出無解關。提出兩道修正並比較 hard-block vs warn-only。

### Human Decision / Review
使用者經 AskUserQuestion 確認：(1) varyHard「應該要有解，是從 edit 匯出的」→ 確立這是編輯器 bug 而非測試用無解關；(2) solver 範圍只取「加開場可行性預檢」（不動逐節點剪枝、不做非阻塞）；(3) 編輯器採「擋下並提示」——還有零件在 tray 時 EXPORT/PLAY 都打不出去。

### Details
- `src/core/Solver.cpp`：新增 `passesBalanceCheck(board, parts)`（O(格數)）——每色 `供給==行約束和==列約束和` 才通過；`Solver::solve` 在搜尋前先呼叫，不通過直接 `return nullopt`。重用既有 `cellCount()`。此為健全的必要條件（所有零件必放 → 每色總佔格固定，須等於各線需求和）。
- `src/main.cpp`：新增 `editorUnplacedCount(ed)`；`exportEditorLevel()` 開頭與新的 `requestPlay()` lambda 各加守門，未全擺上盤面則設訊息「Place all pieces on the board first (N still in tray).」並中止；P 鍵與 EXPORT/PLAY 按鈕統一走守門。

### Verification / Tests Performed
Headless：varyHard 由 **1.4 秒→0.017 毫秒**回 NO SOLUTION（約 8 萬倍）；Example1–6 全部仍 SOLVED（0.02–1.4 ms）。`cmake --build build-release --target game` 乾淨通過。診斷暫存檔已刪除。編輯器守門的 GUI 行為（tray 有零件時按 EXPORT/PLAY 出現提示、全擺好後可正常匯出/試玩）留待實機驗收。

### Result
varyHard 的「無解」被證實為編輯器匯出 bug（非 solver 慢）。solver 現會瞬間拒絕不可能的關卡、demo 不再卡頓；編輯器不再可能匯出/試玩無解關卡。

### Risks / Follow-ups
- 預檢只擋「總格數不平衡」這類必要條件；通過預檢仍可能因幾何擺不下而無解（由既有搜尋處理），符合預期。
- 既有的 `varyHard.txt` 仍是壞檔（在 `cmake-build-debug/assets/levels/`，非正式 `assets/levels/`）；可重進編輯器把所有零件擺好後重新匯出，或直接刪除。
- 守門僅在 GUI 觸發點；headless / 直接呼叫 LevelWriter 仍可寫出未平衡檔——目前無此路徑，暫不處理。

### Other Notes
口試可講點：用「守恆/平衡必要條件」在搜尋前 O(n) 剪掉不可能解，是經典做法；並示範如何用獨立 headless 工具二分定位「是演算法問題還是資料問題」。

## 2026-06-08 — Solver 效能優化：可解硬關卡 7.1s→107ms（預算旋轉格 + 增量剪枝）
Type: Refactor / Debug
Phase: Phase 4（自動解）效能
Feature: Solver 熱路徑優化
Commit: (待 commit)
分支: `fix/stepwise-solve-and-single-hint`

### Context
使用者重匯出的 `varyhard.txt`（12×12、4 色、19 零件、**平衡可解**）通過開場預檢後，實際搜尋要 **7.1 秒**才解出——同步呼叫會讓按 F 凍結 7 秒。需找出並消除瓶頸。

### AI Contribution
用 headless 工具二分 budget：發現 budget 僅 10 萬仍可解卻要 7 秒 → 換算每節點 ~70µs，**節點數其實很少、慢在每節點內部**。零件結構分析顯示 19 個零件全相異（對稱剪枝無用）。定位元凶：`Part::rotatedCells()`（[Part.cpp:87](../../src/core/Part.cpp)）每次都呼叫 `rotatedShape()` **重新配置 `vector<vector<bool>>`**，而 `Board::canPlace/place/remove` 內部都呼叫它；backtrack 的位置迴圈每節點對每個 (旋轉×行×列) 呼叫 canPlace → 每節點上百次堆積配置。提出三道優化並逐一量測。

### Human Decision / Review
使用者要求「確認可以怎麼優化」。先前他在 solver 範圍只選了開場預檢；本次因瓶頸明確（同步凍結 7s）直接動手熱路徑優化並逐步量測驗證，全在 core/Solver 內、不動 `Part`/`Board` 公開介面。

### Details（三步，逐一量測）
1. **增量計數**：把每節點重算全盤的 `exceedsAnyConstraint` 換成維護 `rowCnt/colCnt[color][line]`，放置/移除只加減碰到的格。→ 幾乎沒變（7.16s→6.4s）：證明瓶頸不在剪枝檢查。
2. **「無法達標」剪枝**：再維護 `rowEmpty/colEmpty`，某線「還差格數 > 剩餘空格」即砍子樹（超填剪枝的對偶）。→ 仍 7.1s：證明瓶頸不在節點數。
3. **預算旋轉格（命中）**：新增 `cellsByRot[pos][rotIdx]` 預先算好每零件每旋轉的格子偏移（旋轉格與行列位置無關，卻被重算上百次），並存旋轉 bbox 範圍 `extR/extC` 修剪掃描範圍使位置必在界內；backtrack 改 inline canPlace/place/remove 直接讀寫 `_boardInfo`，hot loop **零堆積配置**。→ **7.1s→107ms**。

葉節點仍用 `WinChecker::isWon` 接受解，確保與遊戲勝利條件一致；剪枝皆為健全必要條件，不漏解。

### Verification / Tests Performed
headless：varyhard 107ms（66×）、Example3 1.36ms→0.068ms，Example1–6 全部仍 SOLVED 且平衡正確（葉節點 WinChecker 通過＝真解）。`g++ -O2` 與 `cmake --build build-release` 皆乾淨無 warning。暫存診斷檔已刪。

### Result
可解硬關卡同步解題從 7.1 秒降到 0.1 秒，按 F 不再凍結；所有既有關卡更快、結果不變。

### Risks / Follow-ups
- backtrack 內 inline 了 canPlace/place/remove（core-to-core），與 `Board` 方法邏輯重複；理由是 `Board` 版每次都會經 `rotatedCells()` 配置，無法在 hot loop 沿用。已加註解說明。風險：日後若改 cell 編碼/放置語意，需同步這段。
- 仍是指數級 backtracking；極端對抗性關卡理論上仍可能很慢，靠 nodeBudget 保底。目前 12×12/19 零件已 107ms，demo 範圍充裕。
- 未動 `Part::rotatedCells` 本身（UI 仍用），只在 solver 熱路徑繞過它。

### Other Notes
口試可講點：用「最小可解 budget」二分法判定瓶頸是節點數還是每節點成本；以及「迴圈不變量提到迴圈外（loop-invariant hoisting）」這個經典優化——旋轉後形狀與擺放位置無關，預算一次即可，把每節點上百次配置降為零。

## 2026-06-08 — Tray 改成滾輪可捲動（零件過多時下方被切掉）
Type: Implementation
Phase: Phase 2/5（GUI）
Feature: 可捲動零件 tray
Commit: (待 commit)
分支: `fix/stepwise-solve-and-single-hint`

### Context
零件多的關卡（如 varyhard 19 個）時，tray 垂直清單 slot i 在 `trayY + i*88`，超過螢幕高度，下方零件看不到也點不到；側板 `panelH` 還跟著 partCount 長到爆。需求：改成滑鼠滾輪捲動式。

### AI Contribution
設計最小侵入方案：把捲動量直接烘進 `Layout::trayY`（`trayY = kTrayViewTop - scroll`），使所有用 `trayY + i*88` 的下游（slot 背景、零件形狀、游標高亮、tray 預覽目標、滑鼠命中測試）自動跟著捲動，免逐處改座標。再以 raylib `BeginScissorMode/EndScissorMode` 裁切固定視口、加捲軸指示、滾輪輸入與夾限、鍵盤選取自動捲到可見。

### Human Decision / Review
使用者直接指示「幫我改成滾輪滑動式的」。屬純 UI 層（Renderer/Input/Layout/main loop），不動 `Part`/`Board`/CMake/相依，依指示直接實作。

### Details
- `Renderer.h`：`Layout` 加 `trayScroll/trayViewTop/trayViewH/trayViewX/trayViewW`；新增常數 `kTrayViewTop=118 / kTrayBottomMargin=84 / kTrayScrollSpeed=56 / kTrayViewX=18 / kTrayViewW=290`；`computeLayout` 與 `Renderer::draw` 加 `int trayScroll=0`。
- `Renderer.cpp`：`computeLayout` 設視口欄位、`trayY=kTrayViewTop-scroll`；`drawSidebar` 改固定高（隨視口不隨 partCount）、"PARTS CACHE" 標籤用固定 `trayViewTop-30`；新增 `drawTrayScrollbar`（內容高於視口才畫，thumb 比例 = 視口/內容、位置 = scroll/maxScroll）；`drawTrayBg` 迴圈、`drawCursor` tray 分支、`drawParts` 的 tray 群組都包 scissor（盤面/手持零件不裁）；`draw` 把 trayScroll 傳入內部 `computeLayout`。
- `Input.cpp`：tray 命中測試加視口 Y 範圍判斷，捲出視口的 slot 不可點；`trayY` 已含 scroll 故 slot 索引自動正確。
- `main.cpp`：in-game 迴圈加 `float trayScroll`（`resetSoundBaseline` 歸零）；computeLayout 前處理滾輪（限游標在 tray 視口上、`-= wheel*speed`、夾 `[0,maxScroll]`）；輸入後做鍵盤選取自動捲到可見；`renderer.draw` 傳入 trayScroll。

### Verification / Tests Performed
`cmake --build build-release` 乾淨無 warning。GUI 行為（滾輪上下捲、捲軸 thumb、捲出的零件不可點、鍵盤上下選取超出視口時自動捲、載入/重開歸零、零件少時無捲軸且行為如舊、拖放/放置不受影響）留待實機驗收。

### Result
零件過多時 tray 可滾輪捲動瀏覽與操作，下方零件不再被切掉；側板高度固定。

### Risks / Follow-ups
- 鍵盤「手持零件且游標在 tray」時，手持零件預覽以未裁切方式畫在捲動後的 slot 位置，極端捲動下可能落在視口外（手持中、即將移動，影響輕微）。
- 視口高度依 `screenH` 計算；視窗極小時以 `kTraySlotHeight` 保底。
- 滾輪僅在游標位於 tray 視口時作用，避免誤捲。

### Other Notes
口試可講點：把「捲動偏移烘進 Layout 座標基準」讓所有下游免改，是減少重複/出錯的關鍵設計；scissor 做視口裁切；繪製與命中測試共用同一套幾何（`trayY` 含 scroll）以避免點擊錯位。
